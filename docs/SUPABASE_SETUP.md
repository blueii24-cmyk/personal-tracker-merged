# Supabase setup (optional account sync, default AI, and Google Calendar)

The app works without hosted configuration: with no Supabase variables, or while signed out, records stay in local app storage. New local partitions start empty. Do not create a replacement project for an existing installation.

## 1. Apply the existing migrations

Use the intended Personal Tracker project and review its current schema/backups first. From the repository root:

```bash
npx supabase@2.122.0 login
npx supabase@2.122.0 link --project-ref <PERSONAL_TRACKER_PROJECT_REF>
npx supabase@2.122.0 db push --dry-run
npx supabase@2.122.0 db push
```

The authoritative migrations, in order, are:

1. `20261101000000_tracker_sync.sql` — tracker records, owner-only RLS, revision guards, and private Google tables.
2. `20261101000001_restrict_client_table_privileges.sql` — removes unsafe default client table privileges.
3. `20261103000000_default_ai_usage.sql` — service-role-only AI rate, daily/global usage, reservation, and spending controls.

Do not replace these with a parallel schema. `node scripts/test-rls.mjs` applies all three twice to a throw-away plain-Postgres database and checks isolation, privileges, revision guards, constraints, and AI quota rollback/settlement. It needs a scratch local Postgres and is not a live Supabase test.

## 2. Configure email authentication

1. **Authentication → Providers → Email:** enable email auth. Keep confirmation enabled for production unless there is a documented compensating control. Do not enable anonymous sign-ins.
2. **Authentication → URL Configuration:** set Site URL to the primary HTTPS app origin and allow-list every exact return URL used:
   - Production web: `https://<YOUR_WEB_ORIGIN>` (or the exact configured `NEXT_PUBLIC_AUTH_REDIRECT_URL`).
   - Android: `com.blueii24.personaltracker://auth/callback`.
   - Add a local web origin only when actually testing locally.
3. Android uses PKCE and exchanges the returned code inside the existing WebView, where its verifier/session are persisted. The custom callback does **not** change the Capacitor WebView origin, hostname, or scheme. Signup confirmation and recovery return to Settings → Account; the auth-state listener adopts the session and starts sync.
4. `NEXT_PUBLIC_AUTH_REDIRECT_URL` is a **web-only** override. Android deliberately chooses its own callback even when that public web value is present in the same build.

## 3. Configure public app values

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<PERSONAL_TRACKER_PROJECT_REF>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<PUBLISHABLE_OR_LEGACY_ANON_KEY>
# Optional fixed WEB return URL:
# NEXT_PUBLIC_AUTH_REDIRECT_URL=https://<YOUR_WEB_ORIGIN>
```

These values are inlined at build time:

- **Local web:** use untracked `.env.local`, then restart/rebuild.
- **Vercel:** configure the existing project for Production (and Preview only with deliberate corresponding Auth allow-list entries), then redeploy.
- **Android/GitHub Actions:** the workflow has browser-safe production defaults. Repository **Variables** with the three names above override them. Rebuild after changing them; an existing APK retains its old values.

Never put a service-role/secret key, Google client secret, refresh token, default-AI provider key, or signing secret in `NEXT_PUBLIC_*`, GitHub Variables, frontend source, Android assets, logs, or chat. Publishable/anon client access is safe only while owner-only RLS and grants remain intact.

## 4. Sync, records, and conflict preservation

- Every write is local first and queued across restart; sync retries after launch/resume, reconnect, explicit request, changes, and the in-app interval.
- Each account has a separate on-device partition. Guest records remain separate until the user reviews a merge.
- Merge keeps cloud-only and guest records, deduplicates stable IDs, and writes a safety copy first. Different versions enter **Needs review**; stale `base_rev` writes cannot silently overwrite newer cloud rows.
- Only exact legacy IDs generated by the old seed code (`demo-meal-<n>`, `demo-tx-<n>`, and `demo-weight-<n>`) are cleaned/excluded. Unknown `demo-` IDs and all legitimate records are preserved. Local/cloud cleanup writes a raw safety copy first and is idempotent; account cleanup propagates tombstones. Imports and merge never offer to upload those known seeds.
- AI keys and Google OAuth tokens are not tracker records and are never synchronized.

## 5. Trusted server functions

- **Default AI:** see [DEFAULT_AI_SETUP.md](./DEFAULT_AI_SETUP.md). The authenticated `ai-chat` function keeps the provider key server-only, builds fixed instructions on the server, restricts model/URL/tools, reserves quotas before provider calls, and never executes tracker tools.
- **Google Calendar:** see [GOOGLE_CALENDAR_SETUP.md](./GOOGLE_CALENDAR_SETUP.md). Its existing server callback requires platform JWT verification off only for `google-calendar`; POST actions still validate the user's JWT internally.

No Next.js server route is needed for either integration, so the static Android export remains intact.

## 6. Required live verification (not covered by compilation)

Use two non-production test users and test devices:

1. Sign up, confirm by email, and confirm automatic session adoption. Test sign-in/out, refresh/restart, recovery, revoked sessions, and safe sign-out with pending changes. On Android, open both confirmation and recovery links and verify return to the app.
2. Create guest records, inspect merge, repeat it, and verify the original local partition and safety copy remain. Confirm no known legacy seed is uploaded and an unknown `demo-` record is preserved.
3. Edit offline on two sessions, reconnect, and verify queue resume, tombstones, conflict review, and no duplicates. Include meals/items, transactions, weigh-ins, chats, settings, calendar preferences, and app-created events.
4. Verify user A cannot read/write user B's rows through the real app/API. Do not substitute a service-role browser client for this test.
5. For default AI, test unauthenticated rejection, per-minute/daily/global limits, provider timeout/compatibility errors, and actual tool writes only through the client service layer. Inspect logs for accidental prompt/key content.
6. For Google, test consent, exact callback, read-only imports, repeat sync, revocation/reconnect, and disconnect. Confirm nothing is deleted in Google.
